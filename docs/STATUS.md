# Gate — build status

Canonical status tracker, living in git so it travels with the code — not a
schedule, an inventory. Items in the same group have no order dependency on

_Last updated: 2026-10-12_

## Already built (31)

- **Core AI qualification gate** — conversational screening, fit or not: QUALIFIED / REJECTED. A rejection is a kind close that names the reason in terms of the visitor's situation; when that reason could change (timing, stage, funding, budget, team size) it invites them back once it does. In Triage mode the visitor never sees a not-a-fit verdict (they still go on to the calendar), so they get a neutral handoff instead; the AI's real message stays on the Lead for the professional (`aiConversationService.visitorFacingMessage`). **REDIRECT is paused (2026-10-12):** in live tests the gate almost never used it, and a prompt rewrite that made it redirect wrong fits (0/8 → 5/8) also sent 2 of 12 ideal clients to a $199 course instead of a call. Paused rather than removed: the `REDIRECTED` enum stays (no migration, older leads still display), direct-purchase offers are left out of the gate prompt, a stray REDIRECT from the model is treated as REJECTED (never fails open), and experts' corrections offer fit / not a fit only. Revisit with a post-rejection approach that can't touch qualified visitors
- **Gate-setup compiler** — turns an expert's 4 answers into a qualification prompt + sample conversation
- **Booking flow** — holds, access codes, slot picking, confirmation
- **Google Calendar integration** — multi-calendar conflict checking, default event calendar; multiple Google calendars per professional already supported
- **Signed, browser-bound OAuth `state`** (`lib/oauth-state.ts`, shared by Google and Outlook connect) — HMAC-signed, 10-minute expiry, nonce matched against an httpOnly cookie scoped to the provider's callback route, and the callback must finish as the same professional who started it. Blocks account-linking CSRF (an attacker's calendar silently attached to a victim's account, receiving their bookings) and the `returnTo` open redirect; `returnTo` is limited to same-origin paths
- **Public branded professional page** — hero, services, testimonials, the gate itself
- **Dashboard** — leads inbox, bookings, calendars, availability, services, access codes, profile, settings
- **Auth** — Google OAuth (`AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET`, separate from the calendar's `GOOGLE_CLIENT_*`; the button only renders once configured) plus **real passwordless email-code sign-in** (`email-login.service.ts`, `EmailLoginCode` model, `/api/public/login-code`, the `email-code` credentials provider): 6-digit code, keyed-hash storage, 10-minute expiry, single use, 5 wrong guesses burns it (cap held in the DB, not memory), per-IP and per-email request limits. Needs Resend in production — without it the request endpoint returns 503 rather than faking a "code sent" screen; in development the code is printed to the server log. Dev-email instant login still disabled outside development
- **Conversation-based AI metering** — 10 / 100 / unlimited (fair use) screening conversations a month by tier; one is used (atomically) only when the gate reaches a decision — abandoned chats and fail-open outcomes are free; exhausted allowance fails open and emails the expert once per period. Briefing, warm-up note and Pattern Report aren't metered. See `docs/decisions/0002-plan-tier-billing-model.md`
- **Server-owned screening conversations** (`QualificationConversation`, `qualification-conversation.service.ts`) — the client sends only its next message, so history can't be forged or padded to drain an allowance; each conversation is capped at `MAX_AI_CALLS_PER_CONVERSATION` (8) and new ones at `MAX_CONVERSATIONS_PER_VISITOR_PER_DAY` (5) per visitor IP per expert. Malformed AI replies are retried, then turned into a follow-up question — only real outages fail open
- **Shared rate limiting** (`lib/rate-limit.ts`) — counters in Postgres (`RateLimitCounter`, hashed keys) via one atomic upsert, so limits hold across Vercel instances; fails open if the database is unreachable. Verified: 30 concurrent requests against a limit of 10 allowed exactly 10
- **Background jobs (manually triggered)** — hold expiry, event-creation retry, calendar sync, token health check, outcome follow-ups, booking reminders, pattern reports, monthly conversation-allowance reset — see `docs/decisions/0004-background-jobs-deferred-inngest.md`
- **Pre-appointment reminder emails** — `send-booking-reminders.job.ts`, sent once per booking ~24h before the slot (`BOOKING_REMINDER_HOURS_BEFORE`), loss-framed copy ("this time is reserved for you"). Gate had zero no-show mitigation before this — the single best-evidenced, cheapest lever for reducing no-shows per real RCT/meta-analysis research, not a speculative mechanism
- **Correction / override loop, feeding the live gate** — professional can confirm or correct the AI's decision on any lead (`Lead.correctedResult`/`correctionNote`); a service's most recent reviewed leads are now also surfaced back into the qualification prompt itself as calibration examples (`aiConversationService.buildLabeledExamples`, active once a service has 3+ reviewed leads) — real feedback, not just captured data
- **Low-friction outcome tracking** — one-click follow-up email + magic-link page, Won/Lost/No response, optional deal value
- **AI Pattern Report** — weekly digest on rejection patterns, objections, and a suggested refinement. Not metered. Also includes a **channel-quality breakdown** (`pattern-report.service.ts`'s `buildChannelBreakdown`) — which referrer/UTM channel sends leads that actually get QUALIFIED (corrections take precedence over the AI's original call), not just which sends the most traffic. Fully deterministic, no AI call, no token cost — computed and included even if OPENAI_API_KEY is unset or the AI narrative half fails
- **Founder-facing admin overview + legal pages** — platform-wide stats at `/admin`; `/privacy` and `/terms` live and linked from the homepage footer
- **Real calendar conflict-checking + provider abstraction** — see `docs/decisions/0001-calendar-provider-abstraction.md`
- **Anonymous visit stitching** — `gate_visitor_id` cookie logs every hit on a professional's page; visits backfill onto a Lead the moment one exists; leads inbox shows the full path, not just the last referrer
- **Embeddable booking widget** — `public/embed.js` + `/embed/[slug]`, see `docs/decisions/0003-embed-widget-frame-ancestors.md`
- **Pre-call briefing** — AI summary of a lead's qualification transcript, cached on the Lead, surfaced in the Bookings dialog before a call. Built ahead of the interview-validation question per direct instruction — worth confirming it's actually wanted once those interviews happen.
- **Visitor warm-up note** (`visitor-warmup.service.ts`) — the briefing's mirror image: the same qualification transcript, turned into a short "Before your call" section in the *visitor's* booking confirmation email (restates their situation with the concrete details they gave, plus up to 3 things to have ready). Built into the existing confirmation rather than a second email. Generated in `postConfirmAsync` alongside calendar event creation, metered against the token balance and skipped once it's exhausted, and skipped without an AI call when the visitor wrote under 80 characters (the model otherwise writes generic filler). Fails open to the plain confirmation; AI text is HTML-escaped
- **Ghost recovery** (`ghost-recovery.service.ts`) — when a lead the professional marked `NO_RESPONSE` comes back to their page (same `gate_visitor_id` browser), the return visit is linked onto the lead's path and the professional gets a "came back" email with how they returned and a one-click email link. Gate never contacts the visitor itself. Runs via `after()` in `/api/public/visits` so the visitor never waits; one alert per lead per `GHOST_RETURN_ALERT_COOLDOWN_DAYS` (7), claimed atomically via `Lead.ghostReturnAlertedAt` so concurrent visits can't double-send. Fails silently
- **Protected time (shadow calendaring, protective-only)** — Control Room "Protected time" card (`protected-time-settings.tsx`): a professional claims a range for a stated goal and Gate never offers it as bookable, even inside weekly hours. Backed by the existing `BlockedDate` model, which slot generation already treated as busy (professional buffers apply to it like any busy range); the UI for it had only lived on the orphaned `/app/availability` page. Times are entered in the profile timezone (not the browser's). Added `PATCH`/`DELETE /api/app/availability/blocked-dates/[id]` — edit/delete on the old page had been silently 422ing against the strict create schema. Deliberately never touches the professional's real calendar (no auto-decline, no reschedule)
- **Plan tier data model + enforcement** — see `docs/decisions/0002-plan-tier-billing-model.md`. Data model and enforcement only — Stripe billing is not built.
- **Dynamic slot priority** — the AI's QUALIFIED call now also carries `isStrongFit` (stored on `Lead`, only ever set by a real AI judgment, never a fail-open path). A professional can mark availability rules `priorityOnly` (held back for strong-fit leads) and set a narrower `Service.standardAvailabilityExposure` window for everyone else. Strong-fit status is re-derived server-side from the `leadId` in both `/api/public/slots` and the hold/confirm slot check in `booking.service.ts` — never trusted from the client. The narrower standard window is applied client-side only (a perk, not a security boundary); priority-only slots are excluded server-side.
- **AI disclosure + value-first fit signal** — visitors are told up front they're chatting with Gate's AI screening assistant (identity form line + the AI's first turn), and the AI confirms honestly if asked. On a clearly strong answer it may affirm the fit mid-conversation instead of staying neutral until the final decision.
- **Outlook calendar integration (code)** — `outlook-auth.service.ts`, `outlook-calendar.service.ts`, `outlook-sync.service.ts`, the `OUTLOOK` branch in `calendar-provider.service.ts`, `/api/app/outlook/{connect,callback}` routes, `OutlookConnectButton` on both calendar UI surfaces. Not usable until the credentials below exist.
- **Test your gate** (`gate-test.service.ts`, `POST /api/app/services/[id]/gate/test`, `components/services/gate-test.tsx`) — in the gate setup's preview and edit screens, one button sends 6 simulated visitors (2 ideal, 2 borderline, 2 wrong-fit, each an AI-invented persona) through the expert's *draft* prompt using the same `aiConversationService.nextTurn` as the live gate, so it can be tested before saving. Each result shows who got in, a readable transcript, and a verdict: as expected, "check this" (ideal client turned away, wrong fit let in, no decision, or an AI error) with a hint on what to change, or "close call" for borderline visitors. Nothing is persisted — simulated visitors never become Leads, so they can't touch the inbox, attribution, reports, or billing. Not metered against `tokenBalance` (a run is ~a cent on gpt-4o-mini); capped at 30 simulated visitors/hour per professional instead. A fail-open fallback is reported as an AI error, never as QUALIFIED (`ConversationTurn.failedOpen`). Calibration examples are loaded only after confirming the service belongs to the caller. Not yet built: correcting a simulated call to feed the calibration loop — that would need simulated leads stored apart from real ones
- **The "not yet" door** — when the gate rejects someone who's the right person at the wrong time (timing, stage, funding, budget, team size), it says so kindly, saves what would need to change on the Lead (`notYetReadyWhen`, e.g. "is ready to start interviewing within the next month"), and invites them back. If the same browser (`gate_visitor_id`) returns to the same service within a year, the gate welcomes them back, asks whether that has changed, and re-screens — coming back alone never qualifies anyone. The old Lead is stamped `notYetReturnedAt`; the new one links back via `answersJson.returningFromLeadId`. The leads inbox has a "Not yet" tab with each person's "ready when" and a "Came back" badge, and Test your gate shows not-yet outcomes. Memory is deliberately limited: cookie only (never a typed email, which anyone could enter to see someone's earlier answers), only not-yet leads, only the same service. Verified live: a not-yet visitor returned, was recognized and qualified; a different browser started cold
- **Must-haves confirmed before qualifying** — the gate-setup compiler now writes a MUST-HAVES section (2–4 hard requirements, editable like the rest); the live gate won't QUALIFY until each is confirmed by something the visitor said, and asks about any that aren't. A QUALIFIED must include the visitor's own words for each must-have; the server checks the quotes against what they actually wrote (exact or ≥80% of meaningful words) and treats missing or invented evidence like a malformed reply — retry with a correction, then a follow-up question, never a fail-open. Older gates without the section get it inferred from their profile. The evidence shows as "Why they qualified" in the leads inbox and in Test your gate. Fixes wrong fits slipping through because the gate decided before asking (e.g. a Head of Marketing qualifying for a CEO-only service); can't catch a visitor who lies
- **Every decision explains itself** — the leads inbox opens each lead with "Why this decision": ✓ each must-have with the visitor's words for a QUALIFIED (plus a one-line reason for a strong fit), ✗ the failed must-have or red flag with the visitor's words for a REJECTED (plus "ready when" for a not-yet), and the plain reason for anyone let through without screening (Open mode, AI unavailable, allowance used up). Each AI decision also keeps the criteria it was judged against and how many of the expert's reviews were shaping the gate, with a nudge to correct it below. Rejection quotes are checked like qualification quotes; one the visitor didn't say is shown as "not said outright", never invented. Test your gate shows the same reasons. Limits: the quote check proves the words are the visitor's, not that they prove the requirement (e.g. "we haven't generated revenue" cited for "has raised funding"), and strong-fit reasons can be generic. Not built yet: visitor-facing explanations or a "request human review" path — a question for the lawyer interviews (GDPR automated decisions, EU AI Act)

## Buildable now (3)


- **Call budget that tightens the gate** — one setting: "I want at most N hours of calls this week." Time as a budget, not empty slots. While the budget has room the gate runs as configured; as it fills, the remaining slots are held back for strong-fit leads only; once spent, new visitors are shown next week's slots rather than turned away. Builds on dynamic slot priority (`AvailabilityRule.priorityOnly`, `Lead.isStrongFit`) and the existing per-day cap (`maxBookingsPerDay`) — mostly a matter of switching priority-only on automatically from weekly budget consumption instead of only via hand-set rules. Strong-fit re-derivation stays server-side, same as today. Possible small follow-up: a "this would be your 5th call this week, 1 over budget" cost line on the manual-approval hold screen. Keep it to the one setting — no per-day/per-service budget variants unless asked.
- **Stripe billing — checkout, subscriptions, webhooks.** The piece that actually moves a professional between tiers and collects money. Blocked on a Stripe account + API keys — can't be built and verified live without them. Policy already decided (see decision 0002): non-payment soft-locks new leads/bookings after Stripe's retry window, existing confirmed bookings are never touched.
- **Outlook credentials** — code is built (see above); blocked purely on a real Azure AD (Microsoft Entra ID) app registration + `MICROSOFT_CLIENT_ID`/`SECRET`. See `.env.example` for the registration steps.

## Gated on post-launch volume (6)

These need real traffic to say anything useful — 6 beta testers don't produce enough rejections or outcomes to learn from.

- **What your hours earn** — attribution × outcomes as value per hour of call time, by channel and service ("LinkedIn calls earn ~€310/hr of your time, website ~€90"). Lives in the weekly Pattern Report. Outcomes are self-reported — label the number as such and never bill on it (decision 0002).
- **Your gate tells you when you're underpriced** — when qualified visitors routinely can't get a slot within ~2 weeks, that's a pricing signal: suggest a rate increase or paid priority slots. Schedulers see bookings, not the demand that couldn't fit; Gate sees both. Pairs with the call budget.
- **A no that still helps** — the expert uploads their own material (articles, guides, a free resource); a rejected visitor leaves with a useful next step from the expert's own work, not just a polite close. Only the expert's own content — no new visitor data. Also gated on the lawyer interviews: an AI quoting legal/medical material is a liability question for regulated professions.
- **Proof of fit for the visitor** — the gate screens both ways: a qualified visitor sees honest evidence this expert fits them (e.g. "most clients in your situation came back to work with them again"), from the expert's own outcomes. Needs real volume and careful wording since outcomes are self-reported.

- **"Your gate designs your next offer" (unmet-demand mirror)** — every scheduler only sees who said yes; Gate also hears, in the visitor's own words, why the people it turns away came. Monthly, cluster REJECTED/REDIRECTED conversations from `Lead.answersJson` into what people actually asked for ("14 people asked for help with fundraising decks — you don't offer that"), size it roughly at the expert's own rates (labeled an estimate), and offer one-click "create this offer": a new `Service` with `idealPersonaDescription` prefilled from the visitors' words via the gate-setup compiler. Future matches get `REDIRECT`ed to it instead of rejected, and attribution shows what it earns. Surfaces as one card a month (natural home: the Pattern Report), no dashboard or settings. Add "can rejected visitors' answers be aggregated like this?" to the lawyer interviews — the Pattern Report already processes this data, but offer-design is a new purpose. Verify "nobody else does this" before using it in external copy.
- **Outcome-trained gate** — today the gate calibrates on the professional's corrections (`buildLabeledExamples`); extend it to learn from WON/LOST outcomes, so it learns what a *client* looks like, not just what a qualified lead looks like. Outcomes feed learning only — billing stays on confirmed bookings (decision 0002), since outcomes are self-reported.
